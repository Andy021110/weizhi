## 0. 开工前的基线校正（重要）

方案 3.1「已实现」列出了 v2 数据模型与候选包流程，但**经核对，这些内容在代码库中不存在**：

- `db.py` 的 `_SCHEMA` 只有 v1 的 7 张表（`cards` / `progress` / `user_state` / `plans`
  / `reviews` / `events` / `notifications`）；
- 全库（排除 `.git`）搜索 `EvidenceClaim` / `LearningPack` / `CardSpec` / `CardVersion`
  只命中 `docs/微知v2后续开发方案.md` 一个文件；
- `reader.py` 的路由里没有任何 `/api/v2`、goal、pack、claim 端点；
- 最新提交 `cacde0d` 只增加了方案文档本身，仓库只有一个 `main` 分支。

因此方案 3.1 描述的是**目标态**，不是现状快照。M1 的真实起点是「在 v1 单体旁新起一条 v2 侧轨」，
而不是「在已有 v2 上重写卡片生成」。

对 M1 的直接影响：方案要求 CardWriter 的输入包含 GoalSpec、相关主张、证据原文，
但**证据层本身不存在**，必须在 M1 内先落一个最小可用版本，否则 CardWriter 没有输入。
检查点据此在方案的两个提交之前插入了 CP1。

另一个现实约束：仓库没有 `config.json`（只有 `config.example.json`），即没有可用的
DeepSeek API Key。这与方案「先做本地 Fake Provider」的要求是一致的——
**M1 全程不依赖真实模型调用，所有集成测试走 Fake Provider**。

## 2. 各检查点的通过门槛

### CP0 基线快照

- `python -m pytest tests/ -q` → `39 passed`。
- v1 的 7 张表结构与 `_migrate()` 行为零改动。

### CP1 证据层地基

**做什么**：新增 `v2_sources`、`v2_claims` 两张表；新建 `evidence.py` 做确定性证据抽取
——段落切分、代码/表格/导航/残句过滤、原文 offset 定位、claim 类型标注。

**通过门槛**：

1. 对含代码块、参数表、导航栏、被截断残句的材料，抽取结果中不含这些噪声；
2. 每条 claim 都能用 `[start, end)` 在清洗后文本中原样取回（`text == clean[start:end]`）；
3. 含数字、版本、日期、百分数的句子被优先标为 `kind=number` 并单独可查；
4. 抽取是确定性的：同一输入两次运行结果完全一致；
5. 单测覆盖上述 4 条，且不访问网络、不调用模型。

**回滚**：两张新表与 `evidence.py` 均为净新增，v1 表与调用链零改动，删除文件即回滚。

### CP2 Provider 抽象与审计缓存

**做什么**：新建 `providers.py`，定义 `TextModelProvider` 协议、真实 `DeepSeekProvider`
与本地 `FakeTextProvider`；新增 `v2_model_calls` 表记录 provider / model / prompt_version /
input_hash / output / latency / cost / retry / error；以 `input_hash` 做幂等缓存。

**通过门槛**：

1. Fake Provider 对同一输入返回确定性输出，供集成测试使用；
2. 契约测试覆盖：超时重试、返回非法 JSON、返回缺字段、缓存命中；
3. 相同 `input_hash` 第二次调用不产生新的模型请求（`call_count` 不增加）；
4. 调用失败时写入一条带 `error` 的审计记录，且不写入半成品产物；
5. 每次调用都留下可查的审计行（provider / model / prompt_version / 耗时）。

**回滚**：`providers.py` 是净新增，v1 的 11 处裸调 `OpenAI` 本阶段**不动**（统一收敛留到后续），
因此 CP2 不改变任何线上行为。

### CP3 CardDraft Schema 与 CardWriter

**做什么**：`schema_v2.py` 定义版本化 CardDraft Schema（`schema_version` 从 `1.0` 起），
输出包含标题、导语、解释段、例子、边界、关键点、迁移任务，且**每个事实性段落带 `cites`
指向 claim id**。`card_writer.py` 组装 GoalSpec + claims 输入，调用 Provider，校验 Schema，
落 `v2_card_drafts` 表。

**通过门槛**：

1. Schema 校验器能拒绝：缺字段、类型错、`cites` 指向不存在的 claim id、`schema_version` 缺失；
2. 用 Fake Provider 端到端产出一份合法 draft 并入库；
3. 输入哈希相同（同一 GoalSpec + 同一批 claim + 同一 prompt 版本）时不重复生成版本；
4. 不引入新的第三方依赖（手写校验器，不加 `jsonschema`）；
5. 本阶段只写 `v2_card_drafts`，**不碰 v1 的 `cards` 表**。

**回滚**：净新增文件 + 净新增表，v1 发布链路不受影响。

### CP4 卡片质量门禁

**做什么**：新建 `card_gates.py`，四项检查：引用覆盖、数字一致性、禁用表达、正文密度。
签名对齐既有惯例 `def check(draft, claims) -> list[tuple[标签, 详情]]`，可直接被
`daily_check` 风格的测试与报告复用。

**通过门槛**：

1. 四项检查各有正例（通过）与反例（拦截）单测；
2. 引用覆盖：事实性段落无 `cites` 即拦截；
3. 数字一致性：正文中出现的数字能在所引 claim 原文中定位到，否则拦截；
4. 禁用表达：命中「值得注意」「在当今时代」等通用填充句即拦截；
5. 门禁失败最多修复一次；仍不合格则 `status=rejected` 且保留失败原因，**不创建候选包**。

**回滚**：门禁只在 v2 侧轨内拦截，不介入 v1 发布，删除 `card_gates.py` 即回滚。

### CP5 A/B 评测脚手架（方案第 11 节「验证它的第一步」）

**做什么**：`eval_ab.py` 对同一批证据分别产出「当前规则版」与「证据约束模型版」，
生成可供盲评的材料包与评分表。

**通过门槛**：

1. 脚本可离线跑通（模型版走 Fake Provider，规则版走现有模板）；
2. 输出盲评材料：两版随机编号，评审人不知道哪个是哪版；
3. 评分维度对齐方案：事实准确、解释深度、同质化、迁移价值、阅读负荷；
4. 脚本**不自动判定胜负**，只产出待填评分表——方案明确要求这一步由人来判断。

**回滚**：只读脚本 + 输出文件，不写业务表。

## 3. 贯穿全程的硬约束

来自方案第 8 节与第 4.1 节，每个检查点都必须遵守：

1. **不得在同一个提交里同时**重写生成逻辑、修改数据库结构、切换默认 UI。
   → CP1 只加表，CP3 只加生成，CP4 只加门禁，UI 切换留给 M6。
2. **确定性职责不交给模型**：URL 与文件安全、快照与哈希、证据定位、数字一致性检查、
   幂等键与缓存、Schema 校验、门禁判定，全部由程序完成。
3. **模型不决定证据真伪**，不改写快照，不绕过候选审核直接发布。
4. 每个提交都记录：行为变化、必要测试、迁移说明、回滚方式。
5. 不引入新第三方依赖（保持「标准库 + feedparser / trafilatura / openai」的现状，
   测试侧仅 pytest）。
6. 不加类型注解、不用 logging——与现有代码风格保持一致（全库 0 处函数签名注解，
   日志统一 `print()` + emoji 前缀）。

### 4.2 CP6：真实模型跑出来的四个问题（Fake 测不出）

在 `~/WorkBuddy/2026-08-12-14-09-12/content-pipeline/config.json` 找到可用的
DeepSeek Key 后，用 3 篇真实文章（HuggingFace Blog / 宝玉的博客 / 量子位）跑了 A/B。
结果如下：

| 指标 | 修正前 | 修正后 |
|---|---|---|
| prompt tokens | 38403 | **6617**（-83%） |
| 门禁通过 | 2/3（1 篇 rejected） | **3/3** |
| 模型调用 | 6 次 | 4 次（模型版，不含 v1 基线） |

四个问题：

1. **证据数爆炸**：1.7 万字的文章抽出 385 条证据，全塞进 prompt。
   → 新增 `evidence.select_claims`（Claim Selector 的确定性最小版）：
   按 kind 权重 + 与目标的相关性打分、去重、取前 24 条，再按 `claim_idx`
   排回原文顺序。语义级 Claim Selector 仍是模型职责，留到 M2。
2. **数字门禁误报**：英文材料写 `September 8, 2026`，模型正确译成
   「2026 年 9 月 8 日」，门禁却因为原文里没有阿拉伯数字 9 判它编造数字。
   → 新增 `schema_v2.normalize_numbers` 归一化英文月份名；真编造（99.2% 之类）
   照样拦得住，有正反两个回归用例。
3. **模型把卡写成了文章**：一次实测写了 13 段 2192 字。
   → `schema_v2` 增加 `MAX_BLOCKS_PER_KIND` 上限，prompt 增加篇幅硬约束。
4. **A/B 基线不公平**：原来的规则版完全没过模型（只是原文拼接），
   而真实 v1 是「整篇正文 + T2 模板 → 模型出卡」。拿无模型基线比有模型方案，
   等于人为抬高模型版。→ 新增 `--rule-baseline v1`，复用 v1 的 T2 模板。
   **评判必须用这个，用 `concat` 得出的结论不成立。**

顺带修正：证据长度下限从 25 字放宽到 15 字——「准确率达 87.5%」这类
带硬数字的短句恰恰是最该保留的证据，之前被误筛掉了。

### 4.3 有意留下的三个未决项

1. **A/B 结论还没出**。盲评材料已生成（`eval_out/`），但评分表要人填。
   方案第 11 节的判定规则是：模型版「事实准确不低于规则版」且
   「解释深度/同质化/迁移价值均分显著更高」才进 M2/M3——这个判断脚本不代劳。
   从已生成的材料看，两版差异是真实的（v1 是 1035-1839 字的通用精读卡、
   无学习目标与迁移任务；v2 是 786-1032 字、带目标/引用/边界/迁移任务），
   但**哪版更有学习价值必须由盲评说了算**。
2. **v1 的 11 处裸调 `OpenAI` 没有收敛**。CP2 只新建了 Provider 抽象，
   没有改 v1 调用点。收敛是有风险的改动，应该在 v2 链路被验证之后再单独做。
3. **没有任何 UI**。方案第 8 节明确禁止在同一个提交里同时改生成逻辑、改库结构、
   切默认 UI，所以候选包审核界面留到 M6。目前 v2 只能通过脚本与单测驱动。

### 一处与方案不同的取舍

方案 3.1 写「每卡两张图」，方案 2.2 又把这条列为未验证假设。M1 没有实现配图——
M3「语义配图与视觉质量门禁」才是它的归属，且 M3 的验收门槛本身就要求
「删除图片后若理解测试不下降，该图应被拒绝」。在 M1 阶段预先堆图会污染 A/B 评测：
盲评比较的应该是「教学重写有没有价值」，而不是「有没有配图」。

## 5. M1 之后

CP5 跑出的盲评结果决定 M2/M3 是否启动：

- 模型版在**事实质量不下降**的前提下显著提高教学评分 → 进入 M2（目标诊断与动态路径）；
- 否则回到 M1 内部调 prompt 与门禁阈值，不进入 M2。

方案第 11 节写得很明确：这一步验证的是「受证据约束的模型重写是否真的比现有模板更有学习价值」。
在盲评结论出来之前，M1 的产出不应被当作既定胜利。
