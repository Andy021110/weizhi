# 部署守则：仓库与线上必须双向同步

> 这份文档是因为**同一个错误犯了三次**才写的。

## 结论先讲

**部署前必须先跑 `python -m deploy.deploy --check`，看到「仅服务器有：无」才能部署。**

```bash
export WZ_PASS='...'                 # 或配 SSH 密钥并留空
python -m deploy.deploy --check                              # 只报告漂移，不改任何东西
python -m deploy.deploy --files weizhi/core/db.py weizhi/serve/web/reader.html
python -m deploy.deploy --files weizhi/core/db.py --force    # 明知要改写服务器内容时
```

> 文件参数用**相对仓库根**的路径。2026-09-12 目录重构后，模块在
> `weizhi/<层>/` 下、前端资源在 `weizhi/serve/web/` 下；传扁平文件名
> （`db.py`）会报「本地不存在」。`deploy.deploy` 也已经是递归收集文件，
> 不再是只扫根目录一层。

## 为什么需要它

本项目已经三次出现「**线上领先于仓库**」——服务器上有仓库里完全没有的功能：

| 时间 | 文件 | 服务器有、仓库没有 |
|---|---|---|
| 第一次 | `db.py` | `ledger_concepts` 台账表 + 三个函数（与浏览器翻译插件的「读前简报」打通） |
| 第二次 | `reader.html` | 整套「阅读待学」界面（入口按钮 / 弹层 / `/api/ledger/from-reading`） |
| 第三次 | `reader.py` | 四条台账路由（`/api/ledger/{mastery,from-reading,encounter,make-card}`）+ `create_card` 的 `source_url_override` |

每一次都差一点被 `scp` 覆盖掉。这类漂移的特征是：

- **不报错、不失败、不影响启动**——功能静悄悄地消失
- **过很久才被发现**，而且发现时已经不知道是哪次部署弄丢的
- 靠人记得手工 diff 是**靠不住**的（我就是靠手工 diff 发现的，但这说明运气成分很大）

根因是**有人直接在服务器上改代码**（线上 `db.py` 的属主是 `501:staff`、日期是 9/10，
说明是从 Mac 直接传的）。这不是错，但它要求部署流程必须能识别方向。

## 守卫的判据

对每个要部署的文件：下载服务器版本，逐行比对。

- 服务器上的每个 `def` / `class` / `function` 定义，本地都要能找到 → **找不到就硬拦**（真丢功能）
- 服务器上的每个路由字符串（`path == "..."`、`fetchJSON("...")`），本地都要能找到 → **同样硬拦**
- 其余「服务器有、本地没有」的行 → **警告，要求人工确认后才 `--force`**

分两级是因为：一律硬拦时，**重构**（把某行换个写法）会被误判成「覆盖了独有内容」。
误报多了人就会习惯性 `--force`，那守卫就废了。所以要让「真丢功能」和「改了某行」
在输出里长得不一样。

## 部署后必须重启常驻服务

`weizhi/` 包里的任何文件都可能被 `weizhi-reader` 这个 systemd 服务加载，
改了就要重启。**改完不重启，线上跑的还是旧代码**——不报错、不失败，只表现为
"改动没生效"。这个坑真踩过：部署完去验证接口，拿到的是旧版本的响应，
差点得出"改动无效"的结论。

（原来的判断是"改到 `reader.py` / `reader.html` / `db.py` 才要重启"，那是一份
手工维护的清单。重构后服务会 import 包内十几个模块，清单必然漏，改成
**只要动的是 `weizhi/` 下的文件就重启**。）

`deploy.py` 已经默认处理：部署了这几个文件就自动
`systemctl restart weizhi-reader`。要跳过用 `--no-restart`（它会大声提醒
你线上还是旧代码）。

cron 任务不受影响——它们每次都是新进程，天然拿到新代码。

## 线上入口是 80 端口，不是 8000

```
正确：http://47.76.25.13/?key=<access_token>      # nginx listen 80 → 反代 8000
错误：http://47.76.25.13:8000/                     # 公网不通
```

`weizhi-reader` 绑的是 `127.0.0.1:8000`（**只监听本机**），公网进来的流量由
nginx 的 80 端口接住再 `proxy_pass` 过去。所以在服务器上 `curl localhost:8000`
一切正常，换成公网 IP 加 `:8000` 就是不通——两个信号一个对一个错，很容易
误判成"服务器挂了"。

**这个坑真踩过**：把 `:8000` 的地址给了用户，对方一直打不开，
排查时才发现端口绑定的差异。验证线上一定要从**公网 IP + 80** 测：

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://47.76.25.13/       # 应为 200
curl -s -o /dev/null -w "%{http_code}\n" http://47.76.25.13:8000/  # 000（正常）
```

另外，nginx 把静态资源（`js|json|png|svg|css|ico|webmanifest`）直接从
`root /opt/weizhi/app` 服务，不走后端。所以改了 `sw.js` / `manifest.json`
这类文件**不需要重启服务**，但要注意它们同样在 `deploy.py` 的同步范围内。

## 结构性防线（比流程更可靠）

`tests/test_ledger_sync.py` 把「仓库必须包含线上已有的东西」写成断言：

- 台账三个函数存在、`ledger_concepts` 表能建、`upsert` 的 added/updated 分支正确
- `reader.html` 里台账界面元素（`ledgerBtn` / `ledgerOverlay` / `showLedger` / 取数路径）都在
- `reader.py` 里台账路由都在（前端调的路由必须真的存在，否则界面在、点了没反应）
- 配图渲染入口（`renderFigures` / `fig-canvas`）不能被未来的覆盖冲掉
- 整段前端 JS 语法检查（前端没有构建步骤，语法错只会在浏览器里炸）

**线上依赖的东西不该只能靠人去记得。**

## 运营脚本已纳入版本管理

服务器上有 9 个运营/调试脚本（`regenerate.py`、`fix_answers.py`、`export_gs*.py`、
`test_3tasks.py` 等，共 274 行），此前不在仓库里。已全部纳入，保持
「仓库 == 服务器」这个不变量成立——不变量只要有一个例外，检查就失去意义。

⚠️ 其中 `regenerate.py` **会清空卡片**才重新生成。它是现场工具，不是常规脚本，
不要顺手跑。

## 另一个重复出现过的主题：本地判卷

同一个模式在复习流程里也出现过：每道题的 `answer` 随卡片下发到浏览器，
前端自己比对——打开开发者工具就能看到答案。已改成服务端判卷
（`review_flow.py` + `/api/question/answer`），并加了前端守卫测试防止改回去。

**尚未处理**：`/api/cards` 仍返回带答案的题库，供阅读页自测与计划任务使用。
那两处在"作答后立刻展开解析"的语境下答案本就要展示，泄题影响小于复习场景，
但严格说仍可被提前看到。`review_flow.seal()` 与 `/api/question/answer` 都是
通用的，把它们迁过去不需要新的后端工作。
