## 1. 上线的是什么

v2 每天生成候选卡片 → 桥接成 v1 卡片格式 → 打 `shadow` 标记 → 落 `cards` 表。
用户在历史里能看到，但**不进推送、不进质检、不进自动修复**。

cron：`0 4 * * * cd /opt/weizhi/app && .venv/bin/python -m weizhi.ops.v2_shadow --limit 1`

三条隔离由 `db.is_shadow_card` 统一实现（判据只写一次）。

## 2. 为什么是影子模式而不是直接替换

方案第 10 节：「在实验完成前，候选内容继续保留人工发布门槛」。
直接接管推送等于跳过全部验证；完全不跑又拿不到可评估的东西。

实测已验证的隔离效果：

| 检查项 | 结果 |
|---|---|
| 影子卡能被前端读到 | ✅ 有正文 |
| 今日荐读候选 | 13 张，**不含**影子卡 |
| 质检候选 | 20 张，**不含**影子卡 |
| v1 服务 | systemd active，30 分钟日志 0 报错 |
| v1 产出 | 正常（pipeline 本轮生成 4 张卡） |

## 3. 上线前的比对救回了一个功能

**部署前比对服务器与仓库时发现：仓库的 `db.py` 比线上落后。**

线上有 `ledger_concepts` 台账（表 + 3 个函数），用于与浏览器翻译插件的
「读前简报」打通，微知作为掌握度权威源（`cards.memory_state`），
概念用 `source_url = "ledger:{norm_id}"` 关联到卡。**仓库里完全没有这段代码。**

按原计划直接 `scp` 覆盖 `db.py`，这个功能会被**静默删除**：不报错、不失败，
只会在某天被发现「台账没了」。

处理方式：以服务器版本为基础，把 v2 增量叠上去。
- 台账补丁（111 行）打到本地版本，一处 hunk 手工补齐
- 双向校验：服务器内容丢失 **0 行**；v2 的 8 张表与全部函数齐全
- 新增 `tests/test_ledger_sync.py`（4 个用例）把这件事钉住

**这条教训值得单独记住**：不能假定仓库是最新的。部署前必须先比对，
尤其是当线上可能有人直接改过服务器文件时（`db.py` 的属主是 `501:staff` +
9 月 10 日的日期，说明它是从某台 Mac 直接传上去的）。
