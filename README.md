# 微知 WeiZhi

> 一个为 AI 从业者做的个人学习管家：每天自动挑出值得读的几篇，生成**每条事实都能回溯到原文**的学习卡片，再按间隔重复推回你面前。全部跑在一台 2C2G 服务器上，模型成本每天两毛钱上下。

## 这是什么

一个**单用户**的自托管学习系统。不是平台，没有多租户，就服务一个人。
它解决的是我自己的问题：每天有不少碎片时间在读 AI 相关内容，读完记不住、也判断不出值不值得读。

四个环节自动串成闭环：

| 环节 | 做什么 |
|---|---|
| **摄取** | 8 个精选源（官方博客 / arXiv / 权威媒体 / 深度博客 / 分析通讯），增量抓取 + 跨源去重 |
| **挑选** | 先建候选池，再两级筛选：程序筛管时效与去重，模型筛管「值不值得读」并给出理由 |
| **生成** | 先抽取可回溯的事实，再据此写作；产出 6 类卡片（词汇 / 精读 / 数学 / 通识 / 技能 / 代码） |
| **复习与自检** | SM-2 间隔重复 + 测验与 AI 批改；每天自动巡检质量，只出「修订候选」，可回滚 |

## 为什么做

我原来的做法是：看到好文章就收藏，收藏夹越堆越厚，一篇也没读完。
问题不在"没有内容"，而在**没有任何机制替我决定今天该读哪一篇**，也没有机制让读过的东西留下来。

所以微知的设计目标只有一句话：**让每天打开它的人读到值得读的东西，并且读完之后留下点东西。**

这句话听起来像口号，但它决定了后面几乎所有的取舍——比如为什么要有候选池而不是"抓到什么产什么"，
为什么质量修复不允许静默改已发布的卡，为什么"没有好内容"时宁可不产出。

## 几个关键判断

一个学习产品"好"可以有很多原因——模型本身强、需求简单、工具好用。
下面这几条是**这个项目里我自己做的判断**，以及它们各自放弃了什么、现在怎么验证。
我把它们放在这里，是因为「产品看起来不错」和「背后有清晰的判断」是两件事。

### 判断一：卡片里的事实必须能回溯到原文

**问题**：最早的版本是"把整篇正文塞给模型，让它写一张卡"。读起来很顺，但你没法核对——
它可能补了自己记得的背景知识，也可能把"某公司高管说"写成"某公司宣布"。

**判断**：把生成拆成两步——先**确定性地**从原文里抽出事实（带位置），再只拿这些事实去写作，
正文里每段标上引用编号。抽不出足够事实的材料，直接不产卡。

**放弃了**：一部分"文采"和生成速度。模型不能自由补充背景，多花一步抽取，
而且有些材料会因为"抽不出足够事实"而被丢掉。

**怎么验证**：卡片底部有信源、来源级别和原文链接；数据库里有 **1659 条**抽出的证据、来自 12 个来源；
正文里的引用编号能对回原文。

<img src="docs/assets/readme/05-source.png" width="330" alt="卡片底部的信源与原文链接">

### 判断二：质量必须被测量，但修复不允许静默

**问题**：模型产出波动大，靠人一张张看不可持续；而"全自动自愈"听起来更酷，却有个问题——
它会**悄悄改掉你已经读过的内容**。

**判断**：每天自动巡检（客观规则 + AI 打分），但只产出**修订候选**，
采纳与否由人决定；每条修复都留记录、可回滚。

**放弃了**：全自动的爽感，以及一部分自动化程度。多了一个"待拍板"的人工程序。

**怎么验证**：质量页可见「检查 19 张 · 通过率 68% · 平均分 4.17」、问题类型分布、
自动修复成功率，以及每条修复的「回滚」入口。**68% 这个数字我没有藏**——
一个会被自己抓出来并修掉的 68%，比一句"质量优秀"可信得多。

<img src="docs/assets/readme/07-quality-trend.png" width="330" alt="质量趋势与可回滚的修复记录">

### 判断三：时效窗口按内容寿命分档，而不是一刀切

**问题**：原来 8 个源共用一个 7 天窗口。于是"20 天前的深度长文"和"20 天前的快讯"
被当成同一件事——长文过了 7 天就再也读不到，而快讯其实过期更快。

**判断**：窗口按**内容寿命**分档：快讯类（官方公告 / 论文 / 媒体）7 天，
深度类（博客 / 分析通讯）30 天；单个源还可以在配置里覆盖。

**放弃了**：配置的简单。现在窗口是一条表，不是一数字。

**怎么验证**：运行日志会把窗口策略打出来；改动当天，一篇 8 月 24 日的深度文章
（19 天前）按新的 30 天窗口产出了卡片——在旧规则下它会被直接拦掉。

### 判断四：「见过」不等于「产过」

**问题**：抓取时会给所有新条目都写上"已见过"的指纹，但后面只有几篇会被挑中产卡。
其余条目**永久变成已见过，再也不会被考虑**。表现是"已见集合有洞"：
某个源 feed 中段一批四个月前的条目从没被处理过，而比它新的和比它旧的却都算见过。

**判断**：指纹只在**这条已经有结论了**时才写——要么被挑中处理过，要么已超出时效窗口。
没被挑中、但仍在窗口内的，留在池子里等下一轮。

**放弃了**：一点存储和一点重复评估的开销（指纹库从 300 条提到 3000 条）。

**怎么验证**：下面这张图是当天真实运行的对照——老规则会让 145 条永久消失，新规则留下 19 条。

![筛选漏斗](docs/assets/readme/funnel.png)

## 它真的在跑

不是能跑起来的 demo，是每天在生产的实例（数据截至 2026-09-12）：

| 指标 | 数值 |
|---|---|
| 首张卡 | 2026-08-19 |
| 累计卡片 | **516 张**（前沿 180 · 计划 131 · 词汇 43 · 数学 36 · 精读 35 · 论文 30 · 原理 23 · 技能 10）|
| 有产出的天数 | 25 天 |
| 抓取源 | 8 个（官方 / 论文 / 媒体 / 深度博客 / 分析通讯）|
| 抽取出的证据 | 1659 条，来自 12 个来源 |
| 自动化测试 | **578 passed**（不调用任何模型 API）|
| 部署 | 一台 2C2G 香港轻量服务器，SQLite 单文件，无外部依赖 |

**模型成本**：调用审计（9-11 起接入）记录到 75 次调用、输入 19.4 万 token、输出 4.2 万 token、
平均延迟 3.6 秒。按 DeepSeek 现行价目表折算约 **¥0.2 / 天**。
口径说明：审计目前只覆盖走统一 provider 接口的链路，巡检与管家那部分调用还没纳入，
所以这个数字是**折算值不是账单**。

## 系统结构

![系统结构](docs/assets/readme/architecture.png)

模块分工：`reader.py`（常驻 HTTP 服务）· `pipeline.py`（采集与产卡）· `evidence.py`（事实抽取）·
`card_writer.py`（受约束的写作）· `daily_check.py`（质量巡检）· `daily_agent.py`（编排与通知）·
`db.py`（SQLite 数据层）· `providers.py`（模型统一出口：schema 校验 / 重试 / 审计）。

数据模型、设计决策与成本模型见 [ARCHITECTURE.md](ARCHITECTURE.md)（[English](ARCHITECTURE.en.md)）。

### 自动化流水线

| 时间（cron）| 任务 | 作用 |
|---|---|---|
| 6:00 / 18:00 | `pipeline.py` | 抓取 8 源 → 候选池 → 两级筛选 → 产卡 |
| 3:30 | `daily_check.py` | 质量巡检打分 → 生成修订候选（可回滚）|
| 3:35 | `daily_agent.py` | 管家决策 → 通知（荐读 / 待拍板 / 周报）|
| 4:00 | `v2_shadow.py` | 影子链路，用来对比新流程的产出 |

## 工程上的可验证性

- **测试**：578 个，覆盖事实抽取、写作门禁、筛选降级、SM-2、SimHash 去重、
  接口密封（答案不下发到浏览器）、只读权限边界等。用临时 SQLite 库隔离，不污染真实数据。
- **调用审计**：每次模型调用记录 provider / model / prompt 版本 / 输入指纹 / 耗时 / 重试 / 错误。
  输入指纹同时是幂等缓存键。
- **决策留痕**：`docs/` 下有 21 篇方案文档，其中
  [范围决策](docs/范围决策-保留降级合并删除.md) 专门记录"**主动砍掉了什么**"，
  [部署守则](docs/部署守则-仓库与线上同步.md) 记录仓库与线上如何保持同步。
- **读写分权**：主人口令与只读演示口令分开，演示角色在服务端被拒绝一切写操作。

## 已知不足

写出来是因为这些比"我很满意"更有信息量：

- **产品自身的成功标准还没有埋点。** 我能证明"卡片被读了"，但证明不了"读完判断变了"。
  这是这个项目最该补的一块——没有它，所有质量指标都只是在衡量**产出**，不是**效果**。
- **调用审计覆盖不全**，所以成本数字是折算而非账单（见上）。
- **推荐排序在小候选池下可能挤压深度源。** 当前先按来源级别排序再截断，
  如果某天快讯类内容填满了候选上限，博客类会被系统性切掉。已知，未修。
- **单用户假设。** 没有多租户、没有账号体系；"给别人看"目前只有一个只读口令。
- **前端是单文件原生 JS**，没有构建和组件化，改动靠渲染测试与纪律兜底。

## 快速开始

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cp config.example.json config.json    # 填 DeepSeek API key、access_token、demo_token
python reader.py                      # 打开 http://localhost:8000/?key=<你的token>

python pipeline.py --limit 2          # 手动抓一轮并生成卡片
python pipeline.py --fetch-only       # 只看候选池，不产卡、不写指纹
python daily_check.py --dry-run --limit 3   # 预览质量巡检（不落盘）
python daily_agent.py --dry-run       # 预览管家决策（不执行）
```

测试：

```bash
pip install -r requirements-dev.txt
python -m pytest tests/ -q     # 578 个，约 45s，不调用任何模型 API
```

## 安全说明

- `config.json`（API key / 口令）已被 `.gitignore` 排除，备份文件 `config.json.bak*` 同样排除；
  公开仓库只使用 `config.example.json` 模板。
- 服务仅监听 `127.0.0.1`，由 nginx 反代；真实来访 IP 通过 `X-Forwarded-For` 传递。
- 只读演示口令可以公开，主人口令不要外传；换口令改 `config.json` 后重启服务即可。
